# Case study: completion verification

**Status: TESTED**

## Problem

A model claiming a task is complete and a task actually being complete are two different facts. Most agent loops only track the first one — completion is just text the model asserts about its own output, with nothing checking that assertion against reality.

## Symptom

Under adversarial testing designed to probe for it, an agent could report a task as done based on its own narrative of what it did, without any independent check that the described action — a file write, a command run, a specific state change — actually occurred and produced the claimed result.

## Root cause

Completion, in a typical agent loop, is generated by the same model whose output is being evaluated. There's no separation between "the model believes/claims this happened" and "the runtime can independently confirm this happened."

## Engineering constraint

The verification signal has to come from evidence the runtime can check independently of the model — file diffs, command exit codes, recorded state transitions — not from a second model re-reviewing the first model's claim, which just relocates the trust problem instead of solving it. It also can't slow down or complicate the ordinary, successful case.

## Solution

A completion-verification layer checks a claimed COMPLETE against runtime-recorded evidence before it's accepted as true, and locks state after a verified completion so the agent can't quietly keep acting — or re-assert completion — once a task is actually closed.

## Measurement

Exercised under deliberate adversarial probing (prompting for premature or false completion claims): the verification layer distinguishes "the model said it's done" from "the runtime has evidence it's done," and rejects unverified completion claims rather than passing them through.

## Why it matters for agents

An agent you can't trust to report its own completion accurately is an agent you have to babysit — every "done" has to be manually checked, which defeats the point of autonomy. Receipt-backed completion, where "done" means the runtime can point to evidence, is what makes it safe to leave a long-running agent unattended.
